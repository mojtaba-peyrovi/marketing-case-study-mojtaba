Column naming recommendations

The current schema works but would benefit from clearer naming before scaling to more analysts.
Current name Problem Suggested name
row_num Carries no analytical value. Row position is implicit in any table and changes if rows are reordered or filtered. Remove entirely, or replace with a stable record_id if deduplication is needed.
Conversion Channel 1 / 2 / 3 Numbers imply a ranking or priority. They actually represent hierarchy levels: broad type → category → specific channel. channel_type, channel_category, channel_name
Monthly Conversions
Yearly Conversions		 Sounds like "conversions aggregated by month/year." Actually means "subscribers who chose a monthly plan" vs "subscribers who chose a yearly plan." The time dimension is unrelated to the plan type. monthly_plan_starts, yearly_plan_starts
Monthly Paid Conversions
Yearly Paid Conversions		 Same ambiguity as above, plus "Paid" is vague — does it mean the plan is paid, or that the customer has paid? monthly_plan_paid, yearly_plan_paid
Share Coupon Used
Share Student Coupon Used		 "Share" is a financial term (equity stake) and a social media term. Here it means "proportion" or "rate." Ambiguous to anyone reading the schema cold. coupon_usage_rate, student_coupon_usage_rate
New Revenue Create Date
New Revenue Invoice Date		 Reads like a date column, not a revenue column. The word "Date" describes the attribution method, not the data type. revenue_subscription_start, revenue_first_payment

End-to-end process

How the analysis was structured, what was assumed, and what the limits are.
1 How the analysis was structured
  • Loaded and cleaned the Excel dataset (1,152 rows × 17 columns) in Python using pandas
  • Separated full dataset from the 434-row subset that has conversion and revenue data
  • Computed derived metrics: CAC, ROAS, trial-to-paid, revenue per conversion
  • Analysed along three dimensions: channel, market, and time (monthly)
  • Generated all outputs at Docker build time so no raw data is processed at runtime
2 Key assumptions made
  • CAC = spend ÷ (monthly paid + yearly paid conversions) — post-trial, not trial-starts
  • ROAS uses New Revenue (Create Date) — subscription start, not first payment
  • UNKNOWN market and channel rows (~25%) are excluded from per-market analysis
  • Rows with null conversion data are excluded from trial-to-paid calculations
  • One anomalous coupon value (1.33 in PR / English / February) is clamped to 1.0
3 Methods and tools used
  • Python · pandas · numpy for all data manipulation (no Excel formulas)
  • IQR method for outlier detection on spend and subscriber columns
  • matplotlib / seaborn for static charts; Chart.js for interactive dashboard charts
  • Flask web framework; Docker for containerisation; GCP Cloud Run for hosting
  • Automated data validation and 11 metric unit tests run at every build
4 Limitations and uncertainties
  • Single year of data — cannot distinguish seasonality from trend
  • No customer-level data — all analysis is at channel × month aggregation
  • 62% of rows lack conversion data — channel efficiency analysis covers only the tracked subset
  • Reallocation model assumes constant marginal CAC — likely optimistic at scale
  • No LTV or churn data — recommendations are based on acquisition cost only

Metric definitions

Every number in this report uses one of these formulas — no exceptions.
Cost per Conversion (CAC)
Marketing Spend ÷ (Monthly Paid Conversions + Yearly Paid Conversions)
Why paid conversions, not all subscribers? A subscriber who starts a free trial but never pays costs money to acquire but generates no revenue. Using only confirmed paying subscribers gives a true picture of acquisition efficiency. This is the industry-standard definition of Customer Acquisition Cost (CAC) for subscription businesses.
~€21
if we divide by all trial starters
vs
€68.97
if we divide by paying customers only ← we use this
Meta 2024: €3,714,189 spend ÷ 53,855 paid conversions = €68.97 per conversion
Return on Ad Spend (ROAS)
New Revenue (Invoice Date) ÷ Marketing Spend
Why Invoice Date? Invoice Date counts only revenue from customers who actually paid — confirmed cash received. Create Date would include trial starters who never convert, overstating how much a channel earns. A ROAS above 1.0× means the channel returns more in confirmed revenue than it costs.
Example: German invoice revenue ÷ €3,309,947 German spend = {{ "%.2f"|format(d.markets[0].roas) }}× ROAS
Blended ROAS
Total New Revenue (Invoice Date) ÷ Total Marketing Spend
Same formula as channel ROAS, applied company-wide. Sums all markets and channels. Useful as a single top-line efficiency number for the CEO — but hides the variation between channels, which is where the actionable insight lives.
Example: €{{ "{:,.0f}".format(d.kpis.total_rev_invoice) }} total invoice revenue ÷ €{{ "{:,.0f}".format(d.kpis.total_spend) }} total spend = {{ d.kpis.blended_roas }}× blended ROAS
Trial-to-Paid Rate
Yearly Paid Conversions ÷ Yearly Conversions × 100
What does this measure? Of all users who started a yearly trial through a given channel, what percentage went on to pay after the 30-day trial ended. A high rate means the channel attracts users who genuinely want the product. A low rate means the channel attracts curious but uncommitted users — the trial converts cheaply but the payment does not follow.
Example: 37,711 Influencer IG yearly paid ÷ 129,965 Influencer IG yearly trials = 29.0% trial-to-paid
Revenue per Conversion (ARPU)
New Revenue (Invoice Date) ÷ (Monthly Paid + Yearly Paid Conversions)
Why use Invoice Date here? Revenue per conversion reflects actual cash received per paying subscriber — the most useful number for understanding subscription value by market. Monthly subscribers pay immediately; yearly subscribers pay after 30 days. Invoice Date captures both correctly.
Example: France invoice revenue ÷ France paid conversions = €{{ "%.2f"|format(d.markets[1].arpu) }} per conversion
Spend Growth % (efficiency gap)
(December value ÷ January value − 1) × 100, calculated separately for spend and for paid conversions
What does the gap show? If spend and conversions grew at the same rate, every additional euro invested would return the same efficiency as the first euro. When spend grows faster than conversions — {{ ef.spend_growth_pct }}% vs {{ ef.conv_growth_pct }}% — each new euro is buying fewer conversions than the previous one. That is the definition of declining acquisition efficiency.
Spend: Jan €347,812 → Dec €593,799 = +{{ ef.spend_growth_pct }}%  |  Paid conv.: Jan 9,750 → Dec 12,909 = +{{ ef.conv_growth_pct }}%
